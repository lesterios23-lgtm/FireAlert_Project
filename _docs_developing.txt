User story: As a resident, I want to register and log in so that I can submit and track my own emergency reports.
Acceptance criteria:
1. Valid registration data creates an account.
2. Duplicate account identifiers are rejected.
3. Passwords are securely hashed.
4. Invalid login attempts return a safe error message.
5. Authenticated requests are required for protected resident features.
6. Residents cannot access BFP-only endpoints.
7. Logout invalidates the applicable session or authentication token.
8. Authentication behavior follows the approved Laravel tutorial and mobile authentication design.
F.2 Fire emergency reporting
User story: As a resident, I want to report a fire emergency so that BFP personnel can review and respond.
Acceptance criteria:
1. The resident can enter the required incident information.
2. The application validates required fields before submission.
3. The backend validates the request independently.
4. A valid report is saved to MySQL.
5. The resident receives a report reference or another approved confirmation mechanism.
6. The initial report status follows the approved workflow.
7. Failed requests do not display a false success message.
8. Duplicate submissions are handled according to an approved retry/idempotency policy.
9. Report timestamps use a consistent documented timezone policy.
F.3 Location selection
User story: As a resident, I want to share my location or select it manually so that BFP personnel can locate the incident.
Acceptance criteria:
1. The app requests location permission appropriately.
2. If permission is denied, the user can use the approved manual-selection workflow.
3. The system clearly identifies whether the location was device-derived or manually selected.
4. Invalid or out-of-scope coordinates are rejected according to the approved geographic coverage rules.
5. The location is displayed on the appropriate map.
6. The application does not claim a location is verified merely because a device supplied coordinates.
7. Sensitive location data is only shared with authorized users and services.
F.4 BFP dashboard
User story: As BFP personnel, I want to see current emergency reports and incident summaries so that I can monitor operational activity.
Acceptance criteria:
1. Authorized BFP personnel can access the dashboard.
2. Dashboard totals come from database queries, not hardcoded demonstration values.
3. Incoming reports can be opened and reviewed.
4. Empty states and loading states are shown correctly.
5. API errors are handled without breaking the entire dashboard.
6. Resident accounts cannot access the dashboard.
Do not invent dashboard metrics that have not been defined.
F.5 Digital incident record management
User story: As BFP personnel, I want to create, review, update, and search incident records so that historical information is organized digitally.
Acceptance criteria:
1. Authorized personnel can create and update records within their permissions.
2. Records are linked to the appropriate emergency report when required.
3. Required fields are validated.
4. Search uses real stored records.
5. Search can support approved filters, such as status, date range, or incident reference.
6. Record changes preserve the integrity of related reports.
7. The system follows an approved policy for deleting, archiving, or correcting records.

User story: As BFP personnel, I want to view reported incident locations on a map so that I can understand where emergencies are occurring.
Acceptance criteria:

4. Reports without valid coordinates are handled explicitly.
5. Map loading and API errors have understandable messages.
6. API keys are restricted and stored appropriately.
7. The system does not label a schematic or sample map as a live operational map.
F.7 Firetruck response coordination
User story: As BFP personnel, I want to record and coordinate a firetruck response so that the response process is visible in the system.
Acceptance criteria:
1. Authorized personnel can associate a response assignment with the appropriate report.
2. The assigned vehicle or identifier is recorded according to the approved design.
3. Assignment and response statuses follow a confirmed workflow.
4. Response events are saved with timestamps when recorded.
5. Changes are reflected in the appropriate resident report view.
6. The system does not directly control a firetruck.
7. The system does not automatically dispatch a vehicle solely because a predictive model identifies a high-risk location.
F.8 Route suggestion and ETA
User story: As BFP personnel, I want to view a suggested route and estimated travel time so that I can support response coordination.
Acceptance criteria:
1. A route can be requested from the configured BFP station location to an incident location.
2. The system checks that both locations are valid before requesting a route.
3. The route and travel-time estimate are displayed when the mapping service returns valid results.
4. Missing routes, service errors, quota errors, and unavailable locations are handled.
5. ETA is explicitly labeled as an estimate.
6. The system does not represent an ETA as a guarantee.
7. The source of the BFP station location must be confirmed before production use.
8. Traffic-aware ETA must not be claimed unless the selected Google Maps service and configuration actually support it.
F.9 Resident status updates and in-app notifications
User story: As a resident, I want to receive updates about my report so that I know its recorded status.
Acceptance criteria:
1. Relevant status changes generate the approved notification.
2. Notifications are associated with the correct user.
3. Residents can only read their own notifications.
4. The application displays read/unread status if included in the approved design.
5. Notification failures are logged and do not silently undo a successfully saved report.
6. Notification delivery behavior is documented.
7. Push notifications are not assumed; confirm whether in-app updates require polling, refresh, or real-time transport.
F.10 High-risk fire incident location prediction
User story: As BFP personnel, I want to review potential high-risk fire incident locations so that I can use historical evidence to support planning.
Acceptance criteria:

2. The geographic unit and prediction horizon are explicitly defined.

6. The model is compared against an appropriate baseline.
7. Evaluation metrics are selected based on the actual prediction target.
8. Predictions are displayed only when supported by a trained, usable model.
